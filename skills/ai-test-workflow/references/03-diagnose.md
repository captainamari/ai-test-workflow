# Prompt 3 — Diagnose execution

读取用户指定的运行报告，以及报告所关联的 inputs、spec.json、cases.json 和生成文件。先核对 report.fingerprint、render 清单与当前产物是否一致；不一致时不要把旧结果用于当前版本验收。

逐条说明实际结果与剧本预期的差异。根据原始日志，将失败归为资料或规则问题、能力缺失、前置未成立、业务行为不符、测试代码问题、执行环境问题或清理失败。证据不足就保留未判定，不仅依据异常名称猜根因。

给出最小修复建议、需要改变的文件，以及修复后应重跑的检查。不要改预期来迁就现有实现，不要隐藏 blocked、skip 或缺失结果，不要自动重试可能重复产生业务副作用的操作。

如用户已授权修复本地生成产物，最多做两次针对性修复；改变 spec 或 cases 后按项目流程重新审核并生成。不要直接篡改已经登记哈希的生成文件。报告应分别列出通过、失败、错误、阻塞和未执行，不把生成文件数当成通过数。
